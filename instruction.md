Matching text against regular expressions is an input-validation and access-control operation — allow/deny lists, request and log filters, and path rules decide what to permit by matching input against a pattern. When a matcher drifts from the standard it was written against, that gap becomes a validation bypass or denial of service.

POSIX 1003.1 fixes one canonical result for any extended regular expression and subject string: the leftmost-then-longest overall match span, plus for each capturing group a span set by the standard's subexpression rule. That belongs to the standard, not any engine, unlike the leftmost-first backtracking Perl or PCRE produce. Report the standard-defined result exactly for every input the disclosed grammar admits.

The spec is under /app/docs: the grammar, the leftmost-longest overall rule, the deterministic subexpression rule, the I/O contract, and worked examples. Samples with standard-defined output are under /app/data. Grading checks output byte-for-byte against the POSIX-defined result over a larger unseen set from the same grammar, recomputed by an independent oracle.

/app/posixmatch reports the result, invoked as posixmatch pattern subject: PARSE_ERROR and exit 1 for an ill-formed pattern, NOMATCH and exit 0 for no match, otherwise a MATCH line with the overall span plus one GROUP line per capturing group, then exit 0. Semantics must come directly from the disclosed rules; Go's regexp package, any third-party regex library, and any C regcomp or regexec call are forbidden and scanned for. Only the rest of the Go standard library is available offline; build details are in /app/docs.
