RAID scrub contract for the staged host under /app/work/raid-root.

The staged root is the only editable RAID inventory. Paths beneath /opt/raid-scrub are protected and must not be rewritten. The protected controller is /opt/raid-scrub/bin/raidscrubctl. The only required agent command is raidscrubctl apply. Optional environment overrides are RAID_ROOT for a relocated staged root and RAID_OUTPUT for an alternate output directory. Defaults are RAID_ROOT=/app/work/raid-root and RAID_OUTPUT=/app/output. Optional flags understood by apply are --threshold for the mismatch authorization threshold, --campaign for the named campaign, --epoch for the repair epoch and generation identity, --urgent for an override of the declared urgent array, --read-error to inject a media error during the parity scrub, and --corrupt-checkpoint to damage the parity checkpoint before the staged root is read. Flags accept either a space or an equals sign between name and value. The controller never touches host block devices under /dev. Real syntax validation uses staged member metadata files and bash -n against notification helpers.

Array identity is the UUID string, not the device basename. Discovery loads RAID_ROOT/etc/mdadm/mdadm.conf in whole, then RAID_ROOT/etc/mdadm/mdadm.conf.d/*.conf in lexical basename order. Every known array must be discovered from a drop-in under mdadm.conf.d rather than from the monolithic mdadm.conf, and drop-in basenames are free as long as they end in .conf. ARRAY lines must declare UUID= values. DEVICE lines must not expand to host /dev/sd* or /dev/nvme* paths; staged members live under RAID_ROOT/var/lib/raid-scrub/members. Assembly must be UUID based. Path based assembly fails uuid_assembly_clean. UUID comparison is case insensitive after normalizing to lowercase hexadecimal with hyphens. A configuration that places the known ARRAY lines only in the monolithic mdadm.conf fails acceptance even when apply still runs.

Degraded boot policy applies only to the RAID1 array named bootmirror. That array may assemble with one missing member when AUTO=yes or when the line contains spare-group=boot and policy file RAID_ROOT/etc/default/mdadm sets BOOT_DEGRADED=yes. The RAID5 array named data5 must refuse unsafe degraded assembly. data5 must set AUTO=-all or POLICY=refuse-degraded in its drop-in, and RAID_ROOT/etc/default/mdadm must set RAID5_DEGRADED=refuse. Any configuration that would assemble data5 with fewer than three active members increments unsafe_repairs and fails acceptance.

Foreign members are declared in RAID_ROOT/var/lib/raid-scrub/members/*/foreign.flag or ARRAY lines carrying foreign metadata. Foreign arrays and foreign members must be excluded from assembly. A foreign member that is still listed as active fails acceptance. Bitmap policy requires internal write-intent bitmaps for bootmirror and fast10, expressed as bitmap=internal on those ARRAY lines. data5 must use bitmap=none. Any other bitmap setting fails the bitmap policy observation.

Global scrub throughput is capped by RAID_ROOT/etc/raid-scrub/speed-limits.conf as speed_limit_min and speed_limit_max integers in kibibytes per second. Accepted restored values are speed_limit_min=1000 and speed_limit_max=200000. After scrub simulation the controller verifies those values are restored into RAID_ROOT/var/lib/raid-scrub/state/speed_limit_min and speed_limit_max. Separately, every known array needs its own throughput ceiling in RAID_ROOT/etc/raid-scrub/io-budget.conf, written one assignment per line as the array name, an equals sign, and the ceiling in kibibytes per second. The file must declare a ceiling for each of the three known arrays and for no other name. Two conditions hold at once. The three ceilings must sum to exactly the global speed_limit_max, because the rebuild scheduler hands the whole global allowance out to the arrays and refuses to leave any of it unassigned or to promise more than it owns. Each ceiling must also be at least the per-array floor published in /app/array-inventory.txt, because an array starved below its floor can never finish a monthly pass. The floors deliberately leave headroom below the global maximum, so more than one distribution satisfies both conditions. A budget that meets the floors but leaves headroom unassigned fails, and a budget that consumes the whole allowance while starving one array below its floor also fails. Report field budget_ok is true only when the file names exactly the three arrays, every ceiling meets its floor, and the sum equals speed_limit_max.

Spare replacement is triaged, not automatic. RAID_ROOT/etc/raid-scrub/urgency.conf declares the single array that is allowed to consume a spare during this campaign, written as the word urgent, an equals sign, and an array name. The standard campaign declares data5 as the urgent array. The --urgent flag overrides the declaration when maintenance staff redirect the campaign to another array. Eligible spares are listed in RAID_ROOT/etc/mdadm/spare-groups.conf as group=path lines whose paths may be relative to RAID_ROOT. A spare is eligible for a group only when the declared path lives inside the directory named for that group and the file exists, so a path that points into another group directory is never eligible. Exactly one spare may activate, it must come from the spare-group of the urgent array, and the ARRAY line of the urgent array must carry that same spare-group. Anything else leaves spare_activations at zero and triage_ok false. Declaring an unknown array as urgent, or omitting urgency.conf, also leaves spare_activations at zero.

Monthly scrub concurrency is controlled by systemd timers under RAID_ROOT/etc/systemd/system. Each known array must have a timer unit whose OnCalendar stanza fires at 03:00 on a single unpadded day of the month. Zero-padded day forms such as *-*-01 or *-*-08 are not recognized and leave the array without a window. Each array has its own permitted day-of-month window published in /app/array-inventory.txt, and the chosen day must fall inside that array's window. Beyond the windows, the three chosen days must be at least seven days apart from one another in every pair, because a monthly pass on this hardware is still running days after it starts and two overlapping passes would exceed the global allowance. A day outside its window, or a padded form, or a missing timer, makes concurrent_scrubs_peak greater than 1. Days that sit inside their windows but closer than seven days to another array leave adjacency_ok false. Both concurrent_scrubs_peak equal to 1 and adjacency_ok true are required.

Rebuild skipping requires each scrub helper under RAID_ROOT/usr/local/lib/raid-scrub/scrub-<array>.sh, or the matching service unit, to refuse work when RAID_ROOT/var/lib/raid-scrub/state/<array>/sync_action equals rebuild. When that skip fires, scrub-events.jsonl must include an event whose event field is scrub_skipped_rebuild for that array. Helpers that always run, or stubs that never inspect sync_action, fail acceptance.

Checkpoint resume reads RAID_ROOT/var/lib/raid-scrub/checkpoints/<array>.offset. A checkpoint whose contents are a single positive decimal byte offset is resumed and increments resumed_scrubs. A checkpoint whose contents contain the upper case marker CORRUPT anywhere is a damaged journal from the failed controller. The marker is matched case sensitively, so lower case text is not a marker. A damaged checkpoint must never be resumed. It must be set aside by renaming it so that the name ends in .offset.bad instead of .offset, which retires the record without deleting the evidence. While any file whose name ends in .offset carries the marker, checkpoint_ok stays false and the affected array cannot count towards resumed_scrubs. Setting the damaged file aside restores checkpoint_ok, and writing a fresh decimal offset for that array restores the resume observation. The standard campaign expects exactly one resumed scrub. Lock files live at RAID_ROOT/var/lib/raid-scrub/locks/<array>.lock. On read-error or authorization failure the lock must be released.

Mismatch repair needs two independent approvals. The first is the array UUID on its own line in RAID_ROOT/etc/raid-scrub/repair.authorize. The second is a change-board record in RAID_ROOT/etc/raid-scrub/repair.quorum, which holds one or more lines written as the word epoch, an equals sign, and an epoch value. Repair is permitted only when that file carries a line matching the epoch that apply is running under, or a line whose value is a single star, which authorizes every epoch. The default epoch is 1 and --epoch selects another. Mismatch counts above the threshold with only one of the two approvals present increment unsafe_repairs, release the lock, and fail acceptance. Report field quorum_ok is true only when repair.authorize carries the data5 UUID and repair.quorum authorizes the running epoch, and quorum_ok is required for acceptance even in campaigns and thresholds where no repair is actually attempted. Monitoring mode, selected with campaign monitor, never repairs. Read errors stop further repair action for that array and must release the lock.

Notifications are produced by RAID_ROOT/usr/local/lib/raid-scrub/notify.sh. The helper must be valid bash, capture array state into RAID_ROOT/var/lib/raid-scrub/alerts/last-state.json before removal notices, suppress duplicate degraded alerts for the same UUID within one apply, and emit a recovery alert that never contains raw serial numbers. Recovery alerts must include the token recovered and the array name or UUID. Duplicate degraded alerts increment duplicate_alerts. A successful recovery increments recovery_alerts.

Output files are written atomically under RAID_OUTPUT. Temporary files use a .tmp suffix and are renamed into place. Previous successful outputs must remain readable until the new generation replaces them. Array lists in outputs are sorted by UUID ascending. No undisclosed pass condition exists. Every threshold, path, field, enum, window, floor, and ordering rule needed for success is stated in /app/raid-contract.txt, /app/array-inventory.txt, /app/acceptance.txt, /app/scenarios.txt, or /app/examples.txt.
